T2. **Signals compared.** Each candidate (herdr `agent_status` working/blocked; `messages.jsonl` message to the agent newer than its last turn; failed-send marker; task file `building`/`handed in`) has cost, misses, verdict. T4. **Last-turn source.** The note names where "agent's last turn" time comes from (herdr field, session jsonl mtime, or other) and shows it on a real sample. If unverified: stated as unverified, with a fail-safe fallback.
T5. **Bare `--resume` cost.** Stated with source (docs or a free probe) or marked "unverified"; no paid API call is made to find out. Does the rule still hold if a resume with no prompt does cost a turn?
T6. **E1 honoured.** Every off-default squad pane moves (no lazy skip); only pending-work panes get a wake. The note says what a pane that `cswitch` fails to move (`FAILED` line) gets: no wake, retried next tick, wake not lost (pending state survives to the retry or is re-derived).
T7. **Wake placement.** After the whole batch (all moved panes back), not inside `cswitch`; reason given. `cwake <pane>` idle-gated; 60 s not-idle -> skip + log line naming the pane; a person's own pane (no `SQUAD_NAME`) never woken by default; retired agents (not in roster / not live) skipped.
T8. **Wake text.** Short, no secrets/tokens/paths to creds, asks to resend failed messages and answer one line if nothing pending. Literal text in the note.
T9. **Rollback.** `CSWITCH_WAKE=off` (and values: `off`, default) named; `off` = today's behaviour exactly (move all, wake none). Test plan includes it.
T10. **Idempotence.** A wake must not repeat every 5-minute tick: say where "already woken for this switch" is recorded (e.g. `cswitch.log` line) and how `pending()` in `cautoswitch` (15-min window) interacts with it.
T11. **Test plan on the stub harness** (`tests/ca_stubs.py`, ADR 0012): per rule branch one case named, listed by file: pending pane woken once; idle no-work pane moved, zero `agent prompt` calls to it in `herdr.log`; not-idle-in-60 s skipped + logged; own pane; `CSWITCH_WAKE=off`; failed move; unreadable messages file. ## Verdict on HANDIN 01 @ 35c89a7 (round 1): FAIL
D1 and D2 are addressed in the note. Two findings remain; both are in the doc/fixtures of this task.

F1. `tests/fixtures/ca/transcript-tail-{idle,working}.derived.jsonl`: records are flattened to `{"type","timestamp","stop_reason"}` with `stop_reason` at top level. A real transcript (checked read-only on the newest `~/.claude-3/projects/-home-chieule-workspace-squad/*.jsonl`) has `stop_reason` at `message.stop_reason`; top level has none. A parser written to this fixture would read the wrong key and never see `end_turn`/`tool_use` on live data (clause 1 and T4 silently dead; fail-direction "not pending" hides it). Also the note says "records carry stop_reason" without the path. Pass: fixtures keep the real record nesting (`type`, `timestamp`, `message.stop_reason`, `message.content[*].type/name`, user `tool_result` records with `is_error`, other keys may be trimmed), still named `.derived`; the note names the exact key paths (`message.stop_reason`, `timestamp`, `message.content[].type == tool_use|tool_result`, `is_error`, `name == SendMessage`), and says that one turn is several `assistant` records (the last-turn rule uses the last one).
F2. Note, "Where the wake happens": ordering of D2. The per-pane loop re-runs `cswitch` for a stuck/FAILED pane (its `pending()` is false after `FAILED`), which writes a new `-> account` line, so it is in flight again when the wake step runs after the loop; the "others woken same tick" claim then depends on the loop having waited for that pane's `done|FAILED` (up to 900 s) first. State the actual order and outcome for: (a) retry ends FAILED again within the wait, (b) retry still running at the 900 s deadline. The stub test for "one FAILED + two pending woken same tick" must cover the retry tick, not only the first tick.
