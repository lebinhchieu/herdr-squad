# BRD-29: the board shows when an agent is waiting on background work

**Done when an agent that sits between turns with a background shell, a Monitor or a subagent running shows as `waiting` (amber) instead of `idle`, its bar stays open across the wait with an amber hatched segment, and the panel shows its `waiting` time.** PO decision 2026-10-14. Cause (verified by the Manager): herdr's `agent_status` comes from Claude's terminal title (`◑` working, `✳` idle), so an agent that started background work is `idle` for herdr although a finishing task wakes it. Claude's status line then shows `· 1 monitor`, `1 shell still running` or `← 1 agent`.

## What I checked on the real socket (read-only, 2026-10-14)
- Method: `{"id": "...", "method": "agent.read", "params": {"target": "<agent name>", "source": "visible", "lines": 3}}` (`target` and `source` are required; `source` is `visible | recent | recent-unwrapped | detection`). Reply: `result.read.text` (plain text, `truncated: true` is normal), `result.read.pane_id`. The same call the `herdr agent read` CLI makes. The agent's name is the roster name (the name `session.snapshot` already gives).
- Sample (dev-board-13, a live pane): the last two non-empty lines are the Claude status line, then the mode line: `⏵⏵ auto mode on (shift+tab to cycle) · ← 1 agent`. So the indicator is at the **end of the last non-empty line**; with `lines: 3` the pane text is about 600 bytes.
- `session.snapshot` returns `agent_status` for every pane in one call, so one tick costs 1 snapshot + one `agent.read` per pane that herdr reports `idle` or `done` (a `working` or `blocked` pane is never read).

## Design (tech decisions, change what is wrong)

### Recorder: a poller writes `waiting`
- **New activity status `waiting`** with an optional `detail`: `"monitor" | "shell"` (a short string; a record without `detail` is valid). Same record shape as today, plus `detail` only on `waiting`. Add `waiting` to `RECORDED_STATUSES` and `BAR_STATUSES`.
- **Poll every `WAIT_POLL_S = 5` seconds** (env `SQUAD_BOARD_WAIT_POLL_S`, like the other `env_seconds`), in its own thread with its own socket connection (`herdr_snapshot` already opens a connection per call), started from `Recorder.run`. The thread shares only the append path (it takes the same file lock, E5) and a small lock-guarded dict `last_recorded: agent -> (status, detail)` that `append` updates; `Recorder.handle` and `sync` read it. Do not poll inside the event-reading loop (it blocks on the socket with no timeout).
- **Per tick,** for each rostered agent whose herdr `agent_status` is `idle` or `done`: `indicator = parse_background(read_text)`; if present and the last recorded status is not `waiting` with the same detail, append `waiting` (+`detail`); if absent and the last recorded status is `waiting`, append `idle`. An agent whose herdr status is `working` or `blocked` is skipped (its own `working` / `blocked` event supersedes `waiting`; a pane that was `waiting` and turns `working` gets its `working` from the event as today).
- **Idle event does not end the bar when background work is on:** on a `pane.agent_status_changed` to `idle` or `done`, do one `agent.read` for that pane first; if the indicator is there, append `waiting` instead of `idle`. This closes the 5 s gap in which an `idle` would end the bar and `waiting` would arrive after it. (If the text is not yet drawn, the next tick still appends `waiting`: the timeline starts a new bar for it, see below; accepted.)
- **`sync` (E4) must not fight the poller:** its "write what the log lacks" compares with the last status. Treat last = `waiting` with herdr = `idle` as equal (no `idle` is written by sync; only the poller clears `waiting`).
- `parse_background(text)` is a pure function, tested against saved samples: look at the **last non-empty line only** (the mode line). Match `(\d+) monitors?` and `(\d+) shells? still running`, either gives the indicator; `detail` is shell before monitor. **Not `← N agent(s)`: it is a standing marker in every live pane (see Comments, 2026-10-14).** Anything else, or a text with no mode line, is no indicator (never invent one). **Collect real samples first:** read the live panes read-only (`herdr agent read <name> --lines 3 --source visible`, never `send-keys`, `prompt`, `focus`, `attach`), save each distinct status-line text as a file in `tests/fixtures/board/panes/` (`monitor-1.txt`, `shell-1.txt`, `agent-1.txt`, `plural.txt`, `none.txt`, `working-no-indicator.txt`, ...). Strip nothing from the text except the user name and path on the first line if they appear. If a form turns up that these patterns miss, add it with a sample; if two squads' Claude versions word it differently, say so in the evidence.
- **Cost rule (hard):** one tick for 13 agents must stay under 1% of a core, measured as `utime+stime` of the board process from `/proc/<pid>/stat` over 60 s against a quiet baseline, by the Developer, in `evidence/BRD-29/cost.md`. Read only idle or done panes; `lines: 3`; no read while herdr is not reachable (the poller backs off with the same `RECONNECT` delays as the recorder and never prints more than one stderr line per outage).
- **Fallback only if the pane text proves unreliable:** the transcript route (pending `run_in_background`/Monitor ids without a `<task-notification>`) is fragile (the Monitor task id is not in the `tool_result`; killed tasks and restarts leave it pending). Do not build it; if the samples show the pane indicator is unreliable, stop and tell tech-board.

### Timeline: `waiting` is a segment inside the bar
- `TimelineBuilder.status`: `waiting` with an open bar opens a **waiting segment** (like `blocked`, kept in `bar["waiting"]`, same fields); it adds a status row like `blocked` does (`row.status = "waiting"`, with `detail`). The bar stays open. A later `working` closes the waiting segment (as it closes a blocked one); `idle` or `done` closes the segment and ends the bar as today; `blocked` closes the waiting segment and starts the blocked one (blocked wins; the two never overlap). `waiting` with **no open bar** starts a bar at that record, self-started, with the waiting segment open (covers the 5 s race above and agents already waiting at first sight).
- Repeated `waiting` records while a segment is open (a `detail` change): close the segment and open a new one only if the `detail` differs; otherwise ignore.
- `finish_bar` adds `waiting: [{start_row, end_row, start_ts, end_ts, duration_s, detail}]` next to `blocked`. State shape grows by that key only.
- Totals: `agents[name]` gets `waiting_s` (sum of the segments' durations, open segment to now). It is **not** part of `working_s` and not in the header `⏱` (a waiting agent is not working), and `blocked_s` is unchanged. A non-live agent's bar closes at its last event as BRD-28 says; a waiting segment closes with it.
- Columns: `column.status` may be `waiting` (the latest recorded status; `STATUS_FOR_EVENT` gains `"waiting": "waiting"`). The Manager-idle alert and the needs-you logic treat `waiting` as **not idle** (a waiting Manager wakes itself; check `manager_idle` and anything else that tests `status == "idle"` or `!= "idle"`, and `headerAnimating`).

### Page
- **Header dot:** amber (`P.yellow`, `#9E7A00`, already in `P`; no new colour), steady, **no pulse** (it is not active, and a pulse would keep the ambient loop at 8 fps; BRD-27's `headerAnimating` must stay false for a waiting-only squad so the page idles). The status word in the mirror and the card `title` is `waiting`; the mirror's `detail` is shown after it (`waiting · monitor`).
- **Bar:** an amber hatched segment (same hatch drawing as the blocked segment, tint of `P.yellow` instead of `P.red`) over the span of each waiting segment. An open waiting segment's end dot is steady (no pulse). Blocked wins visually: no overlap by construction.
- **Panel (BRD-15):** a line `waiting 4m 05s` under the existing blocked line, shown only when `waiting_s > 0`; the mirror carries the same text (`data-` hook like the blocked one).
- **Header totals** `⏱` stay `working_s` only (spec story 16 and 70 behaviour unchanged for working and blocked).
- **Replay** shows waiting from the log like any other status (no live source needed).
