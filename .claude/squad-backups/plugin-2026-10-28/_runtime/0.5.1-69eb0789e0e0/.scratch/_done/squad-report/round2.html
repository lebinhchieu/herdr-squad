Q7 · Q3 re-read: JSON is the only data; split source assets, one inlined HTML

You are right, and it comes out cheaper. AI tokens are spent only when an agent reads or edits a file. So the plugin ships small separate sources (collect.py, template.html, report.css, report.js): a change to the chart code touches one small file. The render step inlines css, js and data into one report.html (browsers block fetch of a local JSON from file://). Nobody reads that generated file. I read your "JSON is enough" as: drop the CSV tables, keep only data.json, and the HTML is just a view of it.

➡️ Yes: data.json only (no CSV); split sources in the plugin; render inlines them into one report.html that no agent reads.

Q8 · Attributing time and tokens to tasks

Fact: only 58 of 429 messages in win-compat carry a task field, so that field alone cannot attribute work. A session often spans several tasks (Tech Lead, QAs). Layers, first match wins: (1) Developer: roster Owns text ("task 01") and its worktree branch name; (2) other roles: the window between a task's first mention (task field, ASK 01:-style prefix, HANDIN) and its PASS; (3) the rest is scope overhead (planning, BA, Manager, retro). The report shows the % attributed, so a weak spot is visible. No change to process.md now.

➡️ Yes: layered attribution, unmatched goes to "scope overhead", show % attributed, no process change.

Q9 · What counts as a return

A FAIL message on a task = one return (win-compat has 12). Per task also show rework time and cost: from the FAIL to the task's next HANDIN. A task with 3 or more returns is flagged, matching the Manager's existing "3 returns" rule.

➡️ Yes: FAIL = return; rework = FAIL → next HANDIN; flag at 3.

Q10 · Time thresholds for the buckets

Gap between two transcript turns ≤ 5 min = working; longer = idle, unless it sits inside a long tool call (background shell, Monitor, or a command with run_suite.py / test runner → waiting) or between a BLOCKED/ASK and its reply (blocking). The 5 min and the test-command patterns live in one small config file, not in code.

➡️ Yes: 5 min threshold, test-command patterns in one config file.

Q11 · Report views

Scope report: header KPIs (total time, tokens by kind, est. cost, returns, % attributed); task table (time by bucket, tokens, cost, returns); role table (same columns, scope-wide); task × role drill-down; per-agent timeline coloured by bucket. Goal / multi-scope rollup: scopes table, totals, role totals across scopes, cost and time share per scope. Sorting and filtering in the page, no server.

➡️ Yes: these views, in-page sort and filter.

Q12 · Second skill: analyze the report

A separate skill (e.g. squad-report-analyze). The collect step also writes a small digest inside data.json: ranked outliers (top cost tasks, longest blocking, most returns, idle share, cache expiries, role cost share, comparison to other scopes). The skill reads only the digest, and drills into the data through a query command only when a finding needs it. If the data is missing or older than the last message, it runs collect first. Output goes to chat as findings plus proposals; it writes nothing and never edits process.md. The Token Coach is left as is (it works at retro from the usage table); a later change could point it at the digest.

➡️ Yes: digest-only reading, query on demand, collect first if stale, chat output, Token Coach untouched.

Q13 · Hook in squad-close

Facts: squad-close --scope retires agents, removes merged worktrees, then moves scopes/S to scopes/_done/S; the Manager's own tab dies last. Proposal: run collect + render first, before retiring (so paths are still scopes/S and the transcripts are complete). --goal builds the goal rollup from its scopes' data.json. A report failure only prints a warning and never blocks the close. --dry-run skips it.

➡️ Yes: report first, then close; failure warns only; goal close builds the rollup; skipped on --dry-run.
