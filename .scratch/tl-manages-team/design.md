## Decisions (each is a rule T1-T6 carry; wording lands in `promote.md`)

1. **Team Lead in M and L, same roles.** M gains the Team Lead, who takes the plan from the Tech Lead; L keeps its name as a signal label with the same roles (Manager FINAL O3). S unchanged. The plan file keeps one format; the Tech Lead writes `## Handover` on S to M, the Team Lead takes the plan file over from it. Moving down: the Manager retires the roles that drop out; their duties move per the duty table.
2. **Spawn split.** The Manager spawns Team Lead, Tech Lead, BA, QAs, Designer. The Team Lead spawns and retires Developers only and edits only its own roster rows (squad-spawn writes the row; the Team Lead fills owns and status with a small script that re-reads the file just before writing). The Manager edits the other rows.
3. **Developer cap in a goal (QA-W Q1, BA O4): a share, not a counter.** The goal Manager divides the cap among running scopes in each Team Lead's briefing; shares sum to at most the cap; a lone scope has the whole cap. Rejected: a count in `squad-spawn` (the cap is overridable per brief and lives in prose; the count needs cross-scope reads).
4. **Only `dev` for the Team Lead (BA O2): enforced twice.** Settings allow `Bash(squad-spawn dev:*)` (the role is the first argument, so a prefix pins it); a squad whose `settings/` copy is older would keep the broad file, so `squad-spawn` itself refuses any role but `dev` when `SQUAD_ROLE=team-lead`. `squad-retire` refuses, for `SQUAD_ROLE=team-lead`, any target whose roster role is not `dev`. QA-W's "cannot be enforced" holds for settings alone, not for settings plus the script.
5. **No `squad-label` change.** `squad-label --agent` stays Manager-only; the Team Lead sets the Developer's title at spawn (`--title`); QAs are not relabelled in M and L (display only).
6. **Disputes (Q3).** Team Lead settles plan, order and assignment disputes; every other dispute goes straight to the Manager (no relay). A Team Lead ruling follows the `FINAL:` rule: sent once, not re-opened, new fact is a new `ASK`.
7. **Blocked panes (Q4).** Nobody relays a blocked pane or permission prompt; the agent's own `squad-notify` toast tells the PO. `STATUS` stays an answer to a check; the Team Lead (S: the Manager) never pushes it before 10 idle minutes.
8. **Summary (Q5, BA O5): `iterations/<n>.summary.md`**, owner the Team Lead (M, L), at most 40 lines: tasks done with evidence links, returns per task, friction for the retro, open items for the PO. The Manager reads it for the retro and check-in, never transcripts. One row in the Files table.
9. **Manager hears from the Team Lead only** (spec B6): an "Always goes to PO" item, a size-change signal, a non-plan dispute that two rounds did not settle, 3 returns on one task (one budget line, O1), the summary. The Manager watches the Team Lead itself (alive, not stuck); it does not poll Developers in M and L.
10. **`--base` in a goal (BA B16).** The Manager checks the base (`process.md` → Inside a goal) and names it in the iteration file; the Team Lead spawns with that base and never picks an unchecked one. Fits.
11. **No byte budget (PO ruling E2, 2026-10-17: "Remove the budget completely").** Supersedes my earlier request to raise it to 23,500 B. T1 deletes the `processlint` size check, the `stays within N bytes` bullet in `agents/manager.md` and the tests that pin either. All other lint checks (60-word limit, hedges and the rest) stay, so growth is still held by the per-bullet rules but no longer by a total. The live `process-log.md` row records the removal (the Manager writes it after the merge). ADR 0006's budget bullets become history: T6 notes the amendment in ADR 0010. T3 touches other hunks of `manager.md`, so it still branches from T1's passed sha and cannot clash.
12. **Version 4.** `process-version: 4`, snapshot `history/process-v4.md` equal to the template, one changelog block listing each changed section (ADR 0005). Headings and the 19-heading pin are untouched.
13. **`--scope` of a Team Lead's spawn is not gated (QA-B note on T5).** A Team Lead could pass another scope's name to `squad-spawn dev`. Accepted: like the cap (decision 3) and the env gate (QA-W A3) it is a guard against mistakes, not a boundary against an agent that ignores its role file; `team-lead.md` tells it to spawn into its own scope. A gate would need the caller's scope compared to `--scope` in `bin/squad-spawn` (T5 is passed); do it only if a real misspawn happens.
14. **Suites (PO note 2026-10-17).** Developers and QAs run only the test files they touch and never the full suite, never two suite runs at once. The Tech Lead decides when the full suite runs (once for a batch, or at the end of the scope or iteration) and runs it itself, so no Developer holds a suite run (the integration Developer merges and runs targeted tests). The rule lives in `process.md` → Safety → Suites (T8); `dev.md` and `tech-lead.md` lose their copies and cite it (also T8: T4 had already handed in, so T8 merges T4's passed commit first and edits only the suite lines); `CLAUDE.md` keeps the runner command and points at the rule (T8); the QA receipt check becomes "read the Tech Lead's receipt if one covers the sha". Unreleased v4 absorbs it (no v5). Rejected: amending T1 and T4 (both already handed in; a return would cost a loop). Cost: the Tech Lead's session now waits on a long run; it runs it in the background. A per-task regression is found late, at the batch run, and returns the named task. Open for the PO: `settings/tech-lead.json` does not allow `python3 tests/run_suite.py`, so the Tech Lead's run asks the PO once per session; I add no project command to a role's allow list.
15. **Model and effort come from the settings JSON, passed as flags** (PO, 2026-10-17). `squad-spawn` reads `model` and `effortLevel` with `jq` from the squad's `settings/<role>.json` (template as fallback) and still passes `--model`/`--effort`. Checked live: a `--settings` file's `model` key is honoured, but an `--agent` frontmatter `model` beats it, so relying on Claude to read the key would be fragile; flags are deterministic and the existing override replay (ADR 0008) stays flag-only. The fallback is per key (squad file, then template), so live squad files without the keys keep today's values with no edit and no warning; only a key in neither warns, never fails. T9, after T3 and T8.

16. **Combine rule (one function, `squadsettings.combine`).** Effective settings = plugin `templates/squad/settings/<role>.json` (T) plus the squad's `settings/<role>.json` (S), in this order:
    - Every list under `permissions` (`allow`, `deny`, `ask`, `additionalDirectories`): T's entries that S's `remove.<list>` does not name, then S's entries not already present. Exact string match, order kept, no duplicates.
    - Every other key (`model`, `effortLevel`, `permissions.defaultMode`, `env`, `hooks` ...): S's value replaces T's value whole (no deep merge). A squad changes a scalar by setting it in its own file (PO E4 rule 3).
    - `remove` is `{"allow": [...], "deny": [...]}` and covers allow and deny rules only (E4 rule 3). Any other key under `remove` is refused. A `remove` entry that matches no template rule gives a warning on stderr naming file, list and entry. The warning never stops a spawn. `remove` drops template rules only: an entry the squad lists itself stays.
    - The generated file holds neither `remove` nor the stamp (decision 17). Claude must never see them.
17. **Opt-in by a stamp (E4 rule 2).** A squad file with top-level `"squadSettings": {"layer": 1, "minPlugin": "<x.y.z>"}` is layered. A file without it is a **full copy and works exactly as today**: it is validated and passed through unchanged, plus one stderr line pointing at `squad-migrate --to layered-settings`. `layer` above the plugin's supported value is refused with "update the plugin" (a future format is never guessed). `minPlugin` is for the PO, shown in the migrate summary and in the `process-log.md` row. **Rejected: layering every file unstamped.** A full copy that dropped a template allow on purpose would silently get it back (privilege widening) the day the plugin updates.
    - **Old plugins cannot warn.** A plugin from before this change reads the squad file raw and ignores the stamp (checked: Claude Code accepts unknown top-level keys silently). No code in the old plugin can print a warning, so the guarantee is made fail-safe instead: the trim never removes `deny` entries (decision 19), so an old plugin still has every deny; it lacks only trimmed allows, which costs extra prompts the PO sees. This corrects the Manager's "an older plugin warns": it cannot; it asks.
18. **Generated file, fail-closed.** `squad-spawn` writes the effective settings to `<home>/roles/<agent>.settings.json` (atomic write; `roles/` is already git-ignored and per agent) and passes that path to `--settings`. Respawn goes through `squad-spawn`, so it rebuilds the file from the current template: a plugin update reaches a live agent at its next respawn. `--dry-run` validates and prints the path but writes nothing. **Claude Code fails open on a bad settings file** (checked: `claude -p --settings bad.json` prints "These settings files did not load, so nothing in them is in effect, including hooks and permission rules" and runs on with exit 0, so a typo drops every deny). So `squadsettings` validates (JSON object; `permissions.*` lists of non-empty strings; `remove` shape) and `squad-spawn` exits 2 on any failure; it never falls back to the raw file. Needs `python3` (already required). `squad-spawn <role> --show-settings` prints the combined JSON (warnings on stderr), needs no herdr pane and no agent name. The stamp and `remove` show as they are removed in the generated file.
19. **Trim (`squad-migrate <squad> --to layered-settings`).** For each `settings/<role>.json` that has a template counterpart and no stamp:
    - Keep S's `deny` entries all, even those equal to the template (fail-safe for old plugins, decision 17; a duplicate costs nothing at combine).
    - Drop S's `allow` entries that the template has. Drop scalars equal to the template's; keep different ones (a squad that wanted a pin sets it differently).
    - Template rules the copy lacks: a missing **allow** goes into `remove.allow` by default (effective permissions identical); a missing **deny** is **adopted by default** (QA-W A16: adopting a deny is the fail-safe direction; `--keep-template-denies-off` writes it into `remove.deny`). It prints each ("template rule not in your copy, kept off"). `--adopt-template-rules` leaves them out of `remove` instead, so the squad takes them. The PO decides at the Manager's yes; the live `team-lead.json` is the first case (it lacks 3 allows).
    - Check, then write: for every file, `combine(template, trimmed)` must equal the original as sets (and, with `--adopt-template-rules`, original plus the adopted rules). A failure restores the backup and exits 1. A backup copy of `settings/` goes to `<project>/.claude/squad-backups/<squad>-settings-<date>[-n]/` first. `--dry-run` prints per file what is kept, dropped, removed, adopted and changes nothing. A stamped file is skipped ("already layered"). Files without a template, and files not named `<role>.json`, are left untouched with a note.
20. **process.md auto-apply (E4 rule 1).** `squad-process auto [--source squad-start|squad-spawn] [--quiet]` (new, in `squadprocess.auto_apply`):
    - Takes an exclusive `flock` on the squad folder, re-plans inside the lock (two spawns at once: the second sees "current").
    - If the plan has no `conflict` section: compose with no resolutions, `apply(yes=True)`. `local` and `local-section` text is kept byte for byte by `compose` (E4 rule 1 only blocks a local edit **in a section the update also changes**). Backup and `process-log.md` rows as in `apply`, plus one row `auto-applied by <source>: no section conflicted; kept local: <headings or none>`.
    - If any section is a `conflict`: write nothing; print one line naming the sections ("process.md is vN, the plugin's is M; <headings> have your edits and the update changes them: not applied"); exit 0. The Manager puts it in the PO inbox and the PO uses `squad-process-update`, as today.
    - Ahead, flat layout, unreadable file or template: write nothing, one line, exit 0. Never blocks a start.
    - **Where it runs:** `squad-start` (all forms) and `squad-spawn` for role `manager` only. Rejected: every spawn. A pod must not see process.md change under it; the Manager spawn is the one place that can tell running roles to re-read the changed sections, which it does from the notice in its first prompt. Deviation from the Manager's "squad-spawn": other roles' spawns do not apply.
    - **One path to the Manager (QA-W A13):** `squad-start` applies, prints the stderr line once and passes the message to `squad-spawn manager` in `SQUAD_PROCESS_NOTICE`; `squad-spawn manager` runs `auto` itself only when the variable is unset. The notice starts with `applied:` or `blocked:`.
    - The Manager's first prompt carries the result: applied (version change, changed sections, backup; "tell running roles to re-read them") or blocked (write it to the PO inbox). `agents/manager.md` gets that one rule (no process.md change, so no version bump).
21. **squad-init writes layered files.** A new squad gets no copy of the templates. It writes `settings/<role>.json` only for a role that needs an addition, stamped; QA blackbox's read denies (`Read(//<code path>/**)`, `Read(//<root>/.worktrees/**)`) and project test commands go in as normal entries. The template's placeholder deny `Read(//CODE_PATHS_SET_BY_SQUAD_INIT/**)` stays in the template (no change) and a squad file removes it with `remove.deny`. "Keep every template deny" becomes automatic.
22. **T9 per-key fallback stays, simpler.** `key_of` reads `model` and `effortLevel` from the combined file: S wins over T per key, exactly today's result, same regex, same warning when in neither. A full copy still passes through (decision 17), so its scalars win as before.
23. **`extractor-role` (Manager FINAL):** its Phase A touches no code; Phase B may touch `bin/squad-spawn` (role list). T12 makes small, separate hunks: the settings block, the `--show-settings` flag, nothing in the role `case`. It tells the Manager the merge sha at once so the other Tech Lead can rebase.

Deploy plan (the PO deploys; the Manager runs the steps on a yes):
1. Merge. Nothing changes for any squad yet (full copies work as before, process.md auto-apply only fires at the next squad-start or Manager spawn).
2. Per squad, the PO says yes to: `squad-migrate <squad> --to layered-settings --dry-run`, read it, then run it (with `--adopt-template-rules` if the PO wants the plugin's newer allows). Teammates pull the trimmed files and need the plugin at `minPlugin` or newer; an older plugin keeps every deny and asks for more permissions.
3. `process.md` updates itself at the next `squad-start` or Manager spawn; a conflict reaches the PO inbox. Rollback: `git revert` the merge; restore `settings/` from `squad-backups/<squad>-settings-<date>`; the process backup is already written by `apply`.
4. The PO bumps nothing by hand: T14 sets the plugin version to the value `minPlugin` names (0.4.0); releasing it is the PO's call.

Risks.
- Plugin updates now widen permissions on layered squads with no review in the squad: a new template allow reaches everyone at the next spawn. Mitigation: `--show-settings`, `remove`, and the plugin's own review (the PO merges template changes). Accepted: it is the point of E3.
- A template rule renamed upstream leaves a squad's `remove` entry dead and the new name active: the "matches nothing" warning is the signal.
- Settings and `process.md` can differ between a teammate's older plugin and the squad folder: see decision 17.

## Migration and deploy notes (Tech Lead owns; the PO deploys, the Manager applies)

- Additive for roles: a squad on version 3 keeps working until the Manager runs the process update (`squad-process check/plan/apply`, PO's yes). The live squad's `process.md` has local edits: the apply reports them as `local` or `conflict` sections, never overwrites silently.
- **A squad's own `settings/team-lead.json` overrides the template** (`squad-spawn` prefers `$squad_dir/settings/$role.json`). The template change does not reach `.claude/squads/plugin/settings/team-lead.json`: after the merge the Manager asks the PO to approve copying the new allow entries into it. Until then a Team Lead's `squad-spawn` asks the PO for permission; the script gate (decision 4) holds either way.
- Order after the PO merges: (1) merge; (2) update the live team-lead settings; (3) `squad-process apply` on the live squad; (4) tell live roles to re-read changed sections. Rollback: `git revert` the merge; the apply writes a backup of `process.md`.
- Existing M scopes already running with a Tech Lead plan owner stay valid; a new Team Lead joins like an S to M move (Handover).

## Risks

- The Team Lead (Sonnet, medium) now carries every HANDIN/PASS/FAIL copy. Mitigation in T2: state lives in the plan file and roster, not in memory; it respawns at 120k from notes. If it still fills fast, the PO may raise its model: a process choice, not a design change.
- Roster has two writers (Team Lead, Manager) on disjoint rows. A lost update is possible only when both write within the same second; each script re-reads before it writes. Accepted.
- Message-volume goal (spec) is judged after the merge by counting Manager-addressed lines in `messages.jsonl`; QA-W also walks the happy path in the role files (AC-6).
