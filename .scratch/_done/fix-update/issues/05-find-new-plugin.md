## Problem
Chieu's answer to E2 (b), with a limit: the update must work from a Manager session pinned at 0.10.2 onward (0.10.2 -> 0.10.3 and later). He moves a 0.10.0 or 0.10.1 session to 0.10.2 by hand: there is no bootstrap support for older pins, and this ticket adds none.

A Manager session of a composed squad runs from its pinned runtime, `$SQUAD_DIR/_runtime/<version>-<sha12>` (a `git archive` folder), and `squad-spawn` puts that runtime's `bin/` first on `PATH` (`bin/squad-spawn:264-276`). In such a session `squad-process` is the old plugin, so `upgrade` and `homes` see the OLD plugin as "the running plugin":
- `squad-process upgrade --check` exits 1 `cannot pin the running plugin (<runtime> is not a git checkout and no installed squad@* entry ... has this folder)` (`bin/squadruntime.py:104-118`); when the runtime is an installed cache it instead compares the old plugin with itself and says nothing changed.
- `homes` would materialise "the target" from the same wrong root.
So the new plugin must be found from outside the running folder.

## Verified facts that shape the design (Tech Lead, 2026-11-21)
Real samples (REV-4); the Developer copies these shapes into the test fixtures, including the idle and the skip cases:
- `~/.claude/plugins/known_marketplaces.json` (also under `~/.claude-2/`, `~/.claude-3/`): a JSON object keyed by marketplace name, each value `{"source": {"source": "directory", "path": "<abs>"} | {"source": "github", "repo": "<o/r>"}, "installLocation": "<abs folder>", "lastUpdated": "<iso>"}`. This machine: `herdr-squad` is `source: directory`, `installLocation` = `/home/chieule/workspace/squad`, the repo checkout this plugin is developed in; `claude-plugins-official` and `ponytail` are `github` entries whose `installLocation` has no `.claude-plugin/plugin.json` named `squad` (must be skipped without error).
- `~/.claude*/plugins/installed_plugins.json`: `{"plugins": {"squad@herdr-squad": [{"installPath", "version", "gitCommitSha", ...}]}}`; on this machine the only entry is 0.1.0 (a stale cache, older than every pin), so a repo checkout is the normal source here and the installed cache the normal source for a marketplace install.
- `squad-process` has two readers of these files already: `_installed_entries` and `_installed_cache` (`bin/squadruntime.py:144-172`; fixture override env `SQUAD_INSTALLED_PLUGINS`).

## Design
1. **One resolver in `bin/squadruntime.py`**, `newest_plugin(running_root)` -> `(root, version, sha, source)` or raises `RuntimeError_(1, ...)`. Candidates, in this order (the first wins a version tie):
   - the running root itself, when it can pin itself (`is_repo_root` or an installed entry: `running_pin` does not raise);
   - every `known_marketplaces.json` `installLocation` that is a git work-tree root (`is_repo_root`) and whose `.claude-plugin/plugin.json` has `"name": "squad"`; sha = `git rev-parse HEAD` (the checkout's own HEAD, dirty or not, as `running_pin` does today);
   - every `squad@*` `installPath` of `installed_plugins.json` that is a directory with a `plugin.json` version; sha = `gitCommitSha`.
   The best is the highest `vkey(version)`. If the running root cannot pin itself and the best candidate is OLDER than the running version, refuse (below): moving a pin backwards must never happen. A running root that can pin itself is always a candidate, so it only loses to a strictly newer one.
2. **Fixture override** for `known_marketplaces.json`: env `SQUAD_KNOWN_MARKETPLACES` (a file path), the same pattern as `SQUAD_INSTALLED_PLUGINS`; otherwise `~/.claude*/plugins/known_marketplaces.json` (a glob, like the installed listing). An unreadable or malformed file is skipped, never fatal.
3. **Delegation in `bin/squad-process` `main`**, only for the commands that mean "the new plugin": `upgrade` and `homes`. Not `upstream`, `lint`, `compose`, `rule`, `who`, `phase`, `team`, `mode`, `runtime`, `prune`, `scaffold` (those act for the running pin and must not move).
   - An explicit `--plugin-root` in argv: no resolution, behaviour unchanged (every existing test passes it).
   - Else call `newest_plugin(DEFAULT_ROOT)`. The result is the running root: run as today. Another root: run that plugin's `bin/squad-process` with the same argv, `[sys.executable, <root>/bin/squad-process, *argv]` through `subprocess.run` (no `os.exec`: Windows), stdin, stdout and stderr inherited, its exit code returned. Env `SQUAD_PROCESS_DELEGATED=<root>` is set for the child; a child that finds it already set never delegates again (so a chain cannot loop).
   - Print ONE line to stderr before running the child: `squad-process: this session runs plugin <running version>; using plugin <version> from <root> (<source>)`, `<source>` = `known marketplace <name>` or `installed cache`.
4. **The refusal** (exit 1, nothing written, same exit code as today's `cannot pin`): when the running root cannot pin itself and no candidate exists, or the best is older than the running version. The text replaces `cannot pin the running plugin ...`: it names the running plugin and version, every place searched (the `known_marketplaces.json` paths and the `installed_plugins.json` paths it read, with how many entries each gave), and the fix in one sentence each: update the plugin checkout or install to a version at least `<running>`, or pass `--plugin-root <new plugin folder>` and `--new-pin "<version> <sha>"` by hand. When the running root CAN pin itself the existing messages are unchanged.
5. **No change** to `materialise`, `find_old_root`, `read_home`, the pin file formats or any file the commands write. The delegated child is the unchanged 0.10.x code running from the newer folder; `homes --apply` therefore materialises the new runtime from the child's own checkout (`git archive`) or installed cache, as today.
6. README.md: one line under `squad-process upgrade` / `homes` ("from a pinned Manager session the newest plugin is found in `known_marketplaces.json` and `installed_plugins.json`; sessions pinned before 0.10.2 move to 0.10.2 by hand").
7. SQ-10: `bin/` and printed text change, so the Developer also runs `tests/test_windows_safe.py`, `tests/test_utf8_helpers.py`, `tests/test_instructions.py` and quotes the result in `## Behaviour`. Run `grep -rl 'cannot pin the running' tests/ bin/ skills/ docs/ README.md` and every hit (known: `tests/test_squadruntime.py`, `tests/test_squadupgrade.py`, `tests/test_squadscaffold.py`; `skills/squad-init/SKILL.md` and `docs/adr/0011` mention it: edit only if the grep shows the changed message, and say which).

## Compatibility, migration, deploy (LC-12, LC-13)
- Additive: no file, pin, overlay or log format changes; the only new inputs are the two fixture env vars and the two JSON files read read-only. A session that can pin itself (repo or installed) behaves as before unless a strictly newer plugin is found: then it uses the newer one, which is the intent.
- Rollback: plugin back to 0.10.1 (nothing is written to any squad by this ticket).
- Deploy order (Tech Lead's plan, Chieu runs it): 1) Chieu moves the Manager session of any squad still on 0.10.0 or 0.10.1 to 0.10.2 by hand (the only manual step; out of scope here, stated in the changelog Deploy line by 03). 2) From 0.10.2 on, `/squad:squad-process-update` finds 0.10.3 and later by itself. 3) After the deploy: from a pinned 0.10.2 session `squad-process upgrade --check --squad-dir <squad>` prints the `using plugin` line and the real check; with no newer plugin installed it exits 1 with the new refusal.
- Known limit, stated in `## Behaviour`: the skill text and the resolver of a pinned session are the pinned version's; a change to this resolver or to SKILL.md in 0.10.3 reaches a session only after it has moved once.

## AC
- AC1 Resolver (unit, `tests/test_squadruntime.py`, one test file extended): with a running root that cannot pin itself (an extracted folder, no `.git`, not in the listing) and fixtures of the real shapes above, `newest_plugin` returns: the checkout when it is newer; the installed cache when it is newer than the checkout; the checkout on a version tie; and skips, without error, a `github` marketplace without `plugin.json`, a marketplace whose `plugin.json` is not named `squad`, an installed entry whose folder is missing, and a malformed JSON file.
- AC2 Never backwards: running 0.10.3 (not pinnable), best candidate 0.10.2 -> exit 1 refusal naming both versions; no child is run (`SQUAD_PROCESS_DELEGATED` unset, no output from a child).
- AC3 Delegation (`tests/test_squadupgrade.py`, extend `Base`): run the squad-process of an extracted runtime (a `git archive` or `PluginCopy` folder, version 0.4.0, no `.git`) with `--squad-dir <scratch squad>` and no `--plugin-root`, `SQUAD_KNOWN_MARKETPLACES` pointing at a fixture whose directory entry is a git checkout of version 0.5.0: `upgrade --check` prints the stderr `using plugin 0.5.0 from <root> (known marketplace <name>)` line, then the same stdout and exit code as today's `go("--check", sq)` for that squad; `upgrade --apply --yes` then writes `plugin.pin` = the 0.5.0 pin (checkout HEAD), proving the new sha, not the runtime's, is pinned. Exit code of the child is the exit code of the parent (cover 0 and 3).
- AC4 Not delegated: `--plugin-root` in argv, a non-listed command (`mode`, `compose`, `runtime`, `upstream`), and a running root that can pin itself with no newer candidate each run in place and print no `using plugin` line. With `SQUAD_PROCESS_DELEGATED` already set, a child that still cannot pin itself exits 1 with the refusal and starts no grandchild.
- AC5 Refusal text (exit 1): no candidates -> the message names the running plugin, both searched files and their entry counts, and the two ways out; nothing is created or changed in the squad folder (`git status`-style listing before/after in the test or the evidence).
- AC6 `homes` delegates the same way: `homes --check --squad-dir <scratch>` from the extracted runtime prints the `using plugin` line and then `homes` output of the newer plugin (one test is enough: the resolver is shared).
- AC7 Evidence quotes one real run in a scratch squad: the runtime of this branch's sha extracted by `git archive` into `<scratch>/_runtime/<version>-<sha12>`, its `bin/squad-process upgrade --check` with `SQUAD_KNOWN_MARKETPLACES` pointing at a copy of the real `known_marketplaces.json` shape whose `herdr-squad` entry is a second checkout with a higher `plugin.json` version: the stderr line, stdout and exit code, plus the refusal run with the fixture file removed. State that a real mid-session pinned Manager was not run (Chieu's check at merge).
- AC8 Technical: SQ-10 files (item 7) pass and are quoted; `tests/test_squadruntime.py`, `tests/test_squadupgrade.py`, `tests/test_squadscaffold.py`, `tests/test_squad_respawn.py` pass (the grep hits); no new skip; no `os.exec*`, no `shell=True`; paths through `os.path`; UTF-8 JSON reads with `utf-8-sig` as `_installed_entries` does; `pkill`-free (SAFE-3).
