Facts that bind the design:
- **The exit code proves nothing** (row 2). Success = the socket accepted a connection, the call ended in 5 s, and stdout+stderr hold no text from the refusal. Judge by a connect test first, never by exit 0 alone.
- **A live socket is one VS Code window** (its extension host listens on it). Dead socket files exist; probe each with an `AF_UNIX` connect (`ss -xlp` showed 1 listener while `find` showed 5 files at one time). Sockets live in `$XDG_RUNTIME_DIR` (`/run/user/<uid>`), else `/tmp`.
- **The WSL way needs the VS Code server's `remote-cli/code` plus a live socket.** The `vscode://` link (today) goes through the Windows app and "opens" the remote again; that is the PO's complaint.
- **Not proven (needs a second window): which window shows the file when two WSL windows are open.** Only one window exists here and it holds `wpw`, not this repo, so "the window that has the project open" does not exist on this machine now. Candidate rules to test when the PO opens `/home/chieule/workspace/squad` in a second WSL window:
  - (a) `code --goto <file>` (no `--reuse-window`) on any live socket: VS Code's own rule is the window whose folder holds the file, else the last active window. Expected to be enough; **unverified**.
  - (b) if (a) shows the file in the wrong window: pick the socket of the window that has the repo open. The only per-window hint I found is the extension host's log folder (`~/.vscode-server/data/logs/<session>/exthost<N>/vscode.git/Git.log`, line `Opened repository (path)`, found through `/proc/<pid>/fd` of the socket's owner). That is fragile (git repos only); use it only if (a) fails.
- **Not testable here: native Windows or macOS** (the board running outside WSL). There the call is `code --goto <file>` on PATH, no socket (`code.cmd` on Windows; argv list, no shell). Nobody has run it; the ticket says so.

## Design notes
- **One module `squadboard_open.py`**, function `open_file(abs_path, env=os.environ) -> {ok, how, why}`; the route is a thin caller. **The call shape (what the BA's stub `code` records): `code --goto <abs path>`**, one argument after `--goto`, no folder argument, no `--reuse-window`, no `--new-window`. Reason: VS Code chooses the window itself (spike rows 3-4; rule (a) below). Passing the repo folder would open a NEW window when no window has it, which breaks the BA's "no window: last active window". So BA AC1/AC3 ("naming the project folder") cannot be tested as written: the stub can show the path of the file of `repo` or `repo2`, not a folder. Told the BA.
  Picks, in order: (1) `code` found on PATH (`shutil.which`; this is the BA's test stub, a native install, or a board started from a VS Code terminal); (2) WSL (`WSL_DISTRO_NAME`) and no `code` on PATH: newest `~/.vscode-server/bin/*/bin/remote-cli/code` with `VSCODE_IPC_HOOK_CLI` set to a live socket (any live one while rule (a) holds; else rule (b)); (3) nothing -> `{ok:false, why:"no-vscode"}` and the page uses the link. `how` names the one used (`path`, `socket`).
- Argv is a list, `shell=False`, `timeout=5`, `encoding="utf-8"` (TC.4), env = copy of `os.environ` plus `VSCODE_IPC_HOOK_CLI`; the file path is the last argument after `--goto`; no user string is built into a shell line. A path starting with `-` cannot happen (absolute path), assert it.
- **Route `POST /api/open?squad=<key>` body `{"path": "<abs>"}`, token header `X-Board-Token`, `application/json`, Host check (same gate as `PUT /api/ui`).** The server accepts only a path it lists itself: resolve it and apply the same `_under` check as `/api/file` (squad folder and `.scratch`), must be a file or folder. No free path. One call at a time (a busy call gives 429, no queue). Answer `{ok, how, why}`; never raises.
- **Page:** click on a file, folder or ticket row calls the route; on `ok` the status line shows `Shown in VS Code: <path>`; on not ok (no VS Code, no live window, timeout) the page uses the `vscode://` link of 30 as before (no regression) and the status line keeps `Sent to VS Code`. The link stays in the `href`, so middle-click and copy still work. Spike fallback choice for "no window has the project": BA/PO (options sent to the Manager).
- **This breaks four written promises**, so it is the Manager's decision before build (ASK sent): TC.2 and TU.5 (only write is `PUT /api/ui`), T30.AC8 / T30.TA8 (no new route), ADR 0020 (read-only board). The route writes nothing in the squad; it starts one local program. ADR 0020 gets an amendment in ticket 38.
- Security notes for QA whitebox: only a listed path, token, Host check, argv list, timeout, one at a time, no body field other than `path`, response never echoes env or stderr text (only a short `why` word from a fixed list: `no-vscode`, `no-window`, `timeout`, `refused`).

## Technical AC
- **T34.TA1 Pick and judge.** `open_file` with stubbed `subprocess.run` and a stubbed socket probe: (1) `code` on PATH -> argv is exactly `[code, "--goto", abs]`, `how=path` (the BA's stub `code` script records it; QA blackbox runs the same); (2) WSL, no `code` on PATH, one live of two socket files, remote-cli present -> uses the live one with the env variable; dead sockets never used; (3) env `VSCODE_IPC_HOOK_CLI` set and live -> `socket`; (4) nothing found -> `{ok:false, why:"no-vscode"}`; (5) the refusal text on stdout with exit 0 -> `ok:false`; (6) timeout -> `why:"timeout"`. Argv is a list, `shell` not set, no path inside a string command. One test with a table of 6 cases.
- **T34.TA2 Route gate.** `POST /api/open` without token 403; wrong Host 403; wrong Content-Type 415; a path outside the squad folder and `.scratch` 403 and `open_file` not called; a `..` path, a relative path, a path starting with `-`, a symlink out, a missing path: all refused (403/400/404), `open_file` not called. "Listed" = under the squad folder or `.scratch` and existing, the rule of `/api/file`; if the BA's AC6(f) means "inside those folders but not in the Files list", say so and I tighten it; a listed file calls `open_file` once with the resolved absolute path; a second call while one runs 429. `GET /api/open` is 404/405 (no read use).
- **T34.TA3 No other write.** The squad folder hash is the same after a session of opens (only `board-ui.json` may change). The diff has no new file write (`grep` TC.2); the only new `subprocess` is in `squadboard_open.py`.
- **T34.TA4 Page.** With a stub `fetch`: click -> one `POST /api/open` with the row's `abs` and the token; `ok` -> status line `Shown in VS Code`; `ok:false` -> the page still sets/uses the `vscode://` link and shows the old status line; no error text, no tab, panel state unchanged (as T30.TA6). A file name `<img onerror=x>` stays text (TU.3). The old `_blank` pins stay true.
- **T34.TA5 Live check (REV-5b).** On this machine QA whitebox starts the board, calls the route for a real file of the dashboard scope, then runs `code --status` through the same socket and reads the window title: it must show the file name. Evidence: the two outputs in `evidence/34/qa-w.md`. No screenshot of VS Code is possible; QA blackbox's by-hand check is the PO's eye, recorded as a note.
- **T34.TA6 Two windows (open until the PO opens a second window).** With the PO's second WSL window on this repo: rule (a) result recorded in the ticket (which window got the file, read from `code --status` titles and the PO's word). If (a) fails, (b) is built and tested the same way, else the Manager gets options. A FAIL of the business AC for several windows is not a code finding until this row is answered.
